# 自律開発サイクルの詳細(調査→設計→実装→テスト)

このドキュメントは `CLAUDE.md` の「ワークフロー全体像」「厳守ルール(ゲート)」で定義される4フェーズサイクルの詳細な仕組みを定義する。`CLAUDE.md` から参照される。フェーズの存在自体・ゲートの数(2箇所)・実装フェーズでメインエージェントがコードを書かない、という原則は `CLAUDE.md` 側の「厳守ルール(ゲート)」が最終的な正であり、本ドキュメントはその実現方法(仕組み)を記述する。

## 設計・実装のレビューループ(自動、最大2ラウンド)

`/design` の設計ドキュメント作成後(人間確認ゲート1の前)と、`/implement` の実装完了後(`/test` の前)には、それぞれ作成者とは別のサブエージェントによるレビューを挟む。**このレビューは人間を介さない自律的なチェックであり、新たな人間確認ゲートを追加するものではない。** 人間確認ゲートは引き続き2箇所(設計後・テスト後)のみ。

具体的な手順(ラウンドの打ち切り方、`PASS`/`MAJOR`の扱い、レビューアーの独立性)は `.claude/skills/review-loop/SKILL.md` の `review-loop` スキルに切り出している。このプロジェクトでの適用は以下の2箇所。

1. 設計後: `review-loop` を `reviewer-agent: design-reviewer`、`artifact: 設計ドキュメント(と対応する調査ドキュメント)`、`author: designer(または呼び出し元)` で実行する。
2. 実装後: `review-loop` を `reviewer-agent: code-reviewer`、`artifact: 設計ドキュメントとワークツリー内の実装差分`、`author: implementer(または呼び出し元)` で実行する。

各ラウンドの判定・主な指摘は、設計ドキュメントの「設計レビュー結果」「コードレビュー結果」欄、テストレポートの「コードレビューからの引き継ぎ」欄に記録する。`design-reviewer`・`code-reviewer` は著者(`designer`/`implementer`)とは**異なるモデル**(`opus`)を使う。同じモデルで書いてレビューすると、そのモデル特有の盲点がレビューでもすり抜けやすいため、別モデルに読ませることでその盲点を補完する。

## 設計ドラフトの壁打ち(grilling)

`/design` は設計ドキュメントの保存後・`design-reviewer` による自動レビューの前に、`.claude/skills/grilling/SKILL.md` の `grilling` スキルを使って人間と壁打ちする(必須)。自動レビューがドキュメント単体を静的に検証するのに対し、grillingは人間との対話で前提・判断の背景を掘り下げる技法であり、**人間確認ゲート(設計後・テスト後の2箇所)を代替・追加するものではない。** 壁打ちが一区切りついても承認したことにはならず、続けて設計レビュー・人間確認ゲートに進む。詳細な手順は `.claude/commands/design.md` の「設計ドラフトの壁打ち(grilling、必須)」節を参照。このスキルは外部プラグインに依存しないリポジトリ独自のものであり、`/design` 以外でも「壁打ちして」等の依頼で汎用的に使ってよい。

## 調査フェーズの並列化(ファンアウト)

1つのトピックの中に、互いの結果を待たずに独立して調べられる観点が複数ある場合(例:「ライブラリ選定」「既存アーキテクチャとの整合性」「パフォーマンス制約」)、`/investigate` は `investigator` サブエージェントを**同一メッセージ内で複数回呼び出す並列dispatch**によって観点ごとに分担調査させてよい。詳細な手順は `.claude/commands/investigate.md` に定義されている。要点は以下。

- 分解は観点が真に独立している場合のみ行う。観点同士が依存する場合や観点が1つしかない場合は分解しない。分解しても2〜4観点程度に留める。
- 各投入先には出力パス(`docs/investigations/_parts/<topic-slug>/<sub-slug>.md`)を明示し、investigator自身にパスを決めさせない。
- **並列実行中のサブエージェントは `docs/memory/` に直接書き込まない。** 複数エージェントが同時に `MEMORY.md` を編集すると内容が競合・上書きされるため、各エージェントは再利用可能な知見を「メモリ候補」として最終報告に含めるに留め、実際の書き込み(重複排除を含む)は全員の完了後にorchestrator(呼び出し元のメインの会話)が1回でまとめて行う。
- 全観点の結果が揃ったら、矛盾がないか確認したうえで単一の `docs/investigations/YYYY-MM-DD-<topic-slug>.md` に統合する。観点間で結論が食い違う場合は黙って一方を採用せず「未解決の疑問」として残す。
- この並列化パターンは調査フェーズ専用に定義しているが、設計・実装・テストの各フェーズで同様に独立したサブタスクへの分解が可能だと判断した場合、同じ原則(出力パスの明示、共有メモリへの書き込みはorchestratorに集約)を踏襲して拡張してよい。

## ワークツリー分離(複数セッション対応)

このプロジェクトは、複数のセッション(異なるターミナル/チャットから起動された複数のClaude Codeインスタンス)が同時に同じリポジトリを修正することを想定している。共有の作業ディレクトリを複数セッションが同時に書き換えると、チェックアウト中ブランチの奪い合い・コミットの混線・`docs/memory/MEMORY.md` 等の共有ファイルの競合が起きるため、**`/investigate` の開始時点でトピック専用の git worktree を作成し、`/design` → `/implement` → `/test` まで同じワークツリーを使い続ける。**

具体的な作成・入室手順(ベースブランチの決定、`git worktree add`を直接使う理由、既存ワークツリーへの入り方)は `.claude/skills/topic-worktree/SKILL.md` の `topic-worktree` スキルに切り出している。`/investigate`・`/design`・`/implement`・`/test`・`/hotfix` はいずれもこのスキルを呼び出す(`topic-slug`・`branch-prefix`(`feature`または`hotfix`)・`base-branch` を渡す)。(このサイクルの外で、単発・アドホックに作業を分離したいだけの場合は代わりに `.claude/skills/using-git-worktrees/SKILL.md` を使う。トピックサイクル中は `.claude/worktrees/<topic-slug>/` 以外のディレクトリを使わない。)

### このプロジェクトでの適用

1. `/investigate` が最初に `topic-worktree` を呼び出し、トピック専用のワークツリー・専用ブランチ(`feature/<topic-slug>`、障害対応時は `hotfix/<incident-slug>`)を用意する。
2. `/design`・`/implement`・`/test` は同じ `topic-slug` で `topic-worktree` を呼び出し、このワークツリー内で継続する(既に存在するため再作成はされない)。実装フェーズでは複数の `implementer` が並列で動くことがあるため、コミットは原則としてメインエージェントがタスク単位でまとめて行う(詳細は「実装フェーズのタスク分割・並列化」節)。ベースブランチとは分離されているため、こまめなコミット自体は安全。
3. `/test` のゲート2で人間が「承認してクローズ」を選んだ場合にのみ、`.claude/commands/release.md` の手順でトピックのブランチをPR経由で `develop` → `main` の順に反映する(直接pushはしない。詳細は `docs/process/git-workflow.md`)。develop向けPR・main向けPRそれぞれのマージ実行直前には必ず `AskUserQuestion` で人間に確認する。developへのマージ後は、人間による動作確認("打鍵確認")が完了するまでmain向けPRを作成しない。マージ・PRいずれかでコンフリクトが発生した場合、またはCIチェックが失敗した場合は自動解決せず人間に報告する。反映が完了したら(詳細は `CLAUDE.md` 厳守ルール8参照)ワークツリーとブランチを削除する(削除自体は `topic-worktree` スキルの範囲外で、`release.md` が行う)。
4. ゲート2で「修正依頼」「設計からやり直し」が選ばれた場合は、ワークツリーを削除せずそのまま残し、同じブランチ内で作業を継続する。

### 複数セッションでの並行作業

セッションAがtopic Xを、セッションBがtopic Yを同時に `/cycle`(または個別コマンド)で進めている場合、それぞれ別のワークツリー(`.claude/worktrees/topic-x`、`.claude/worktrees/topic-y`)・別のブランチで作業するため、調査・設計・実装・テストの全フェーズでファイル競合は起きない。ただし以下は既知の制限であり、このリポジトリでは未対応:

- あるトピックのワークツリーは、作成された時点のベースブランチの状態(特に `docs/memory/`)を引き継ぐ。作成後にベースブランチへマージされた他トピックの決定・規約は、このワークツリーには自動反映されない(通常の git worktree の性質上の制限)。長時間かかるトピックでは、`/design` 等の途中でベースブランチの最新を取り込むべきか判断してよい。
- 複数トピックのブランチが同時にベースブランチへマージされる場合、`docs/memory/MEMORY.md` など共有ファイルでマージコンフリクトが起きる可能性がある。この場合もゲート2の手順どおり自動解決せず人間に報告する。

## 実装フェーズのタスク分割・並列化

`/implement` を実行するメインエージェント(オーケストレーター)は、**自分でコードを実装しない。** 設計ドキュメントの実装ステップをタスクに分割し、依存関係のないタスクは `implementer` サブエージェントへ並列dispatchし、進捗を確認・記録する役割に徹する。

具体的な手順(`TaskCreate`でのタスク化、トピックプレフィックス、依存関係の整理、ウェーブ単位の並列dispatch、コミット・共有メモリ書き込みの取り扱い)は `.claude/skills/task-parallel-dispatch/SKILL.md` の `task-parallel-dispatch` スキルに切り出している。`/implement` はこのスキルを `topic-slug: <topic-slug>`、`worker-agent: implementer` で呼び出す。詳細は `.claude/commands/implement.md` も参照。

このプロジェクト固有の要点:

- タスク分割・`implementer`への委譲は必須。実装ステップが1つしかない場合でも省略せず、メインエージェントが直接ファイルを編集することはない。
- タスクはトピックをまたいで1つの共有リストに並ぶため、`task-parallel-dispatch`スキルのトピックプレフィックス絞り込みを必ず使う。他トピックのタスクには触れない。
- コードレビュー(`code-reviewer`、`.claude/skills/review-loop/SKILL.md`)は全タスク完了・コミット後に1回行う。`MAJOR`判定の修正も新しいタスクとして`TaskCreate`し`implementer`に委譲する(メインエージェントが直接修正しない)。

## 成果物の命名規則

`YYYY-MM-DD-<topic-slug>.md` で統一する。同一トピックの調査・設計・テストは同じslugを使い、相互にリンクを張ること(例: 設計書の冒頭に対応する調査ドキュメントへのリンクを置く)。`docs/process/git-workflow.md` が定義するブランチ名(`feature/<topic-slug>`・`hotfix/<incident-slug>`)もこのslugと対応させる。

## サブエージェントの使い分け

- **investigator**: 読み取り専用に近い調査(Web検索・コード探索)。実装はしない。
- **designer**: 調査結果を踏まえて設計書を書く。コードは書かない。DBスキーマ変更を伴う設計は `db-designer` に委譲する。
- **db-designer**: `designer` から、テーブル新設・スキーマ変更・データモデリングを伴う設計のときだけ呼び出される補助エージェント。外部Skill(`database-schema-designer`。skills.sh からインストール)を使ってDBスキーマ部分(テーブル定義・正規化・インデックス・制約方針)の案を作り、テキストで呼び出し元に返す。自分では設計ドキュメントを書かない(`designer` が「アーキテクチャ・変更概要」内の「DBスキーマ設計」小見出しに転記する)。詳細は `.claude/agents/db-designer.md`。
- **frontend-designer**: `designer` から、フロントエンドのディレクトリ構成・コンポーネント配置の判断を伴う設計のときだけ呼び出される補助エージェント。feature単位の分割・feature内のFSD由来セグメント分割(`api`/`model`/`hooks`/`types`/`ui`、依存順は`api → model → hooks → ui`)・bulletproof-react由来の共有層(`shared/components`等)を組み合わせた、このリポジトリの標準アーキテクチャに沿って構成案を作り、テキストで呼び出し元に返す。自分では設計ドキュメントを書かない(`designer` が「アーキテクチャ・変更概要」内の「フロントエンド構成」小見出しに転記する)。詳細は `.claude/agents/frontend-designer.md`。
- **design-reviewer**: designerとは別の視点で設計書をレビューする。自分では書き直さない。
- **implementer**: `TaskList`で割り当てられた単一タスクの範囲だけを実装する。設計にない範囲を勝手に広げない。並列dispatch中は自分でコミットも共有メモリへの書き込みも行わない。
- **code-reviewer**: implementerとは別の視点で実装をレビューする。自分では修正しない。
- **tester**: 実装を検証し、レポートを書く。テストを通すためにテスト自体を歪めない(テストコードの改変は原則implementerの担当に戻す)。

各フェーズはメインの会話コンテキストを汚さないよう、可能な限り対応するサブエージェント(Agent tool)に委譲する。**特に実装フェーズは、メインエージェントが自分で実装することを禁止し、`TaskCreate`/`TaskUpdate`/`TaskList`によるタスク分割・並列dispatch・進捗確認を必須とする。**
