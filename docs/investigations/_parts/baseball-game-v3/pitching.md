## 1. 結論: 不足トップ10(影響度順)

総評: 現行の守備は「**球種とセルを選んで『投げる』ボタンを押し、結果の文字が出るのを待つ**」だけで、**プレイヤーの腕前が結果に一切効かない**(結果はすべて乱数)。パワプロの投球にある「指でコースを決める」「ゲージを止める」「狙いどおりに行った/外れた」という手応えが無い。ユーザーの「投げるのもカス」はこの構造的な欠落が主因と推測する(ユーザーの具体的なコメントは未確認)。

| # | 不足 | 根拠(種類) | 影響度 |

| 1 | **腕前の要素が無い。投球の精度は乱数だけで、人間と CPU 投手に差が無い。** ゲージも、タイミングも、指の精度も、結果に影響しない | `deliverPitch`(`model/pitch/delivery.ts`)は狙いセルの中心にガウス誤差を足すだけ。人間は `aimSigmaScale = 1`、CPU は `easy 1.4 / normal 1.0 / hard 0.75`(`cpu/difficulty.ts`)。つまり**人間は CPU「ふつう」と同じ腕前で、CPU「むずかしい」より下手**。[式] | 最大 |

### 2.2 1 球の操作手数 [式]

- 初期選択は「ストレート・中央(2,2)」で、**選択は投球後も保持される**(`GameScreen.tsx`)。
  - 同じ球を続ける: **1 タップ**(「投げる」)
  - 球種だけ変える: 2 タップ。コースだけ変える: 2 タップ。両方変える: **3 タップ**(球種・セル・投げる)
- 飛行中・演出中でもチップとセルは触れる(選択の事前変更ができる)。ただし #4 のとおり、飛行中に触ると 3D の狙い枠が新しい選択へ動いてしまう(コード上の推測。未確認)。
- 打撃側は「ほぼ 1 タップ(タイミング勝負)」、守備側は「選んで押すだけ」で、**守備の入力は時間・位置の精度を一切問わない**。

### 2.3 時間(待ち時間)の見積もり [式]

前提: 通常速度(`fast` なし)、投手イブキ 143km/h(球速差 slider −12 / curve −30 / fork −15)。飛行時間 D = 190000 / 球速(km/h)。

| 球種 | 球速 | D(ms) |
| --- | --- | --- |
| ストレート | 143 | 1329 |
| スライダー | 131 | 1450 |
| フォーク | 128 | 1484 |
| カーブ | 113 | 1681 |

1 球のタップから「次の球を投げられる」までの時間(ストレートの場合。自然に放置した場合で、タップでスキップすればこれより短くなる):

| 結果 | 内訳 | 合計 |
| --- | --- | --- |
| ボール/見逃し | windup 0.70s + D 1.33s + テロップ 0.5s + 余韻 0.2s | **約 2.7s** |
| 空振り | windup 0.70 + D 1.33 + (D〜D+70ms にテロップ開始)+ 0.7 + 0.2 | **約 3.0s** |
| ゴロ(飛距離 30m 前後) | windup 0.70 + D 1.33 + 滞空 1.15(= 250 + 30×30)+ テロップ 1.1 + 0.2 | **約 4.5s** |
| フライ(飛距離 60m 前後) | windup 0.70 + D 1.33 + 滞空 2.68(= 1000 + 28×60)+ 1.1 + 0.2 | **約 6.0s** |
| ファウル | windup + D + 滞空(1.3〜3.1s、`foul` の距離 12〜75m)+ 0.7 + 0.2 | 約 3.9〜6.0s |

- 「投げる」を押してから**ボールが見えるまで 0.7 秒**(windup。この間ボールは非表示)。ボールが見えてから着弾まで 1.3〜1.7 秒(CPU 打者はそのうち D−150ms で判定が通知される)。
- 結果は着弾の後に出る。**打球は落ちるまで(最大約 2.7s)結果が分からない**(テロップが落下時から)。
- スキップ: 演出中に画面タップ(または Space/Enter)。1 タップ余分に必要。
- 目安: 3 回制で自分が守る 3 つの半イニングが約 17 球 × 約 4s ≒ 1 分強ずつ(推測)。

### 2.4 投球のブレ(狙い vs 着弾)の数値 [式]

- σ = `baseSigma 0.28 × (1 + (100 − control 63)/100 × controlSigmaFactor 1.0)` = **0.384**(ゾーン単位)。疲労は球数 58 球超から効き始める(`pitchesPerStamina 2.2 × stamina 66` = 145 球が上限、残量比 0.6 を下回ると σ が増える)。3 回制では通常効かない。
- 狙いセルの中心からの着弾誤差(平均半径)= σ√(π/2) = 0.481 単位 ≒ **24〜27px(画面)**。1 セル(0.667 単位)の画面上の大きさは約 33×37px。
- 参考(既存の使い捨て計測、デスクトップの旧版、4 球のみ): 狙いと着弾の距離 0.07 / 0.28 / 0.33 / 0.22(平均 0.23)。標本が少なく、式の期待値 0.48 とも合わないので、**参考にとどめる**。([scratchpad/tester/desktop-pitching.json] `/tmp/claude-0/-home-user/41656968-7fcb-53f0-b4ad-be1c855b6111/scratchpad/tester/desktop-pitching.json`)

| 狙い | ストライクになる確率(式) |
| --- | --- |
| 中央(2,2) | 約 98% |
| ゾーン角(1,1) など | 約 65% |
| ゾーンの縁の中段(1,2) | 約 81%(x 方向だけ縁。1 軸 0.807 × y 軸 0.99) |
| ボール球の外周(0,2) | 約 19%(ボール球を狙っても 19% はストライクに入る) |

### 2.5 CPU 打者の反応 [式]

- 結果に表れる反応は、打者の「振る/見る」と、振った場合のバットとテロップだけ。**球種・コースを変えて投げても、打者の構え・反応は変わらない**(CPU は `swingProbability` がゾーン内 0.40/外 0.22、2 ストライクで +0.2、3 ボールで ×0.4 のみ)。
- 守備側の他の野手(内野手・外野手)は、打球時にだけ走る。投球前後の守備位置の反応(構え、バックアップ)は無い。
- 結果テロップ: ボール / ストライク / 空振り! / ファウル / 打球の結果(ヒットなど)。見逃し三振・空振り三振・フォアボールは専用文言。

### 2.6 音・振動 [式]

- `Audio`・`vibrate` は frontend のソース全体で 0 件。**完全に無音・無振動**。

## 4. 修正案の選択肢(効果・工数・リスク)

注: 以下は選択肢の整理であり、決定ではない。工数は S(〜半日)/M(1〜2 日)/L(3 日以上)の目安(推測)。

### 案A: 現行 UI を残した「投げ応え」改善パック(部品単位で選べる)

| 部品 | 内容 | 効果 | 工数 | リスク |
| --- | --- | --- | --- | --- |
| A1 | 「投げる」→リリースの windup を 700ms → 約 250〜300ms に短縮(`cpuWaitMs` を CPU 待機と分離) | テンポ(#7)。1 球 0.4s 短縮 | S | CPU 側の待機と共用の値なので分離が必要。投球モーションが速すぎて見えにくくなる |
| A2 | 着弾の σ を下げる(例: `baseSigma` 0.28 → 0.15 で狙いセル到達 38% → 約 80%。式) | 「狙ったところに行く」(#2) | S | CPU 投手も同じ式なので `aimSigmaScale` で調整が必要。`balance.test`・既存テスト(`delivery.test` 等)の再調整。**腕前の要素は戻らない**(#1 は未解決) |
| A3 | 狙いを投球時点に固定し、着弾後 0.5〜0.8s は着弾点リング+狙い枠を重ねて残す(「ズレ」を見せる) | フィードバック(#4) | S〜M | 演出時間が延びる。打撃側の `plan` と競合しないか確認 |
| A4 | 球種チップに球速・矢印(曲がり方向)を付ける | 球種の違い(#5) | S | 画面が狭い。曲がりの見た目 5〜13px の弱さは残る(`bendGain` 引き上げは別論点) |
| A5 | 効果音(ミット音・空振り・打球音)を Web Audio で合成して追加(外部素材なし) | 無音(#9) | M | 自動再生制限(最初のタップで解放が必要)、ライセンス素材を使わない前提なら合成音の品質が課題 |
| A6 | 投球時に投手を大きく見せる(短いズーム/カメラ寄せ)、打者が格子を隠さない配置 | 投げた感(#8) | M | 構図の既存設計(`framing`・`safeArea`)と衝突。打撃側にも影響 |

- 総合効果: 中。ユーザーの「パワプロとは程遠い」に対しては部分解(腕前要素が無い点は残る)。
- 総合工数: S〜M。リスク: 小〜中。

### 案B: 現行グリッドを残し、**投球ゲージ(タイミング)**を足す(アプリの A タイプ寄り・簡易)

- 内容: 球種・セルは現行どおり選ぶ。「投げる」を押すとゲージが動き、**もう一度タップで止める**。止めた位置で σ の倍率が決まる(ナイス = 大幅に小さい、普通、赤 = 失投としてボール球ゾーンまたは中央へ)。ゲージの色の意味・ナイスピッチゾーンは公開情報のとおり簡略化する。
- 効果: 大(腕前要素が入る。#1・#2・#7 の「待つだけ」を解消)。
- 工数: M〜L。`PitchCommand` に精度(0〜1)を足す、`deliverPitch` の入力追加、人間のタップ時刻を `event.timeStamp` から求める(タッチ遅延補正が要る = 既存の打撃と同じ)、ゲージ UI、ボットによる試算。reducer・乱数消費数に触れるため既存の単体テスト(決定論の固定値)に影響。
- リスク: スマホの入力遅延(ピットフォール [[game-feel-needs-playability-check]]。ゲージは時間窓を狙う入力なので、遅延補正とボット試算が必須)。SwiftShader では実入力が 0.2〜1 秒遅れる([[swiftshader-playwright-input-latency]])ので、E2E はページ内計測にする。

### 案C: ゾーン直接指定(ドラッグ)+ゲージ(パワプロアプリ A/B タイプに最も近い)

- 内容: 球種チップを選ぶ(または押したまま)→ 3D のゾーン上を**相対ドラッグ**で狙い(連続座標のカーソル)を動かし、離して確定 → ゲージを止める。5×5 の抽象グリッドは廃止(または補助表示)。
- 効果: 最大(「パワプロらしさ」に最も近い。#1〜#4 を同時に解消)。
- 工数: L。`PitchCommand.cell` を連続座標に広げるか、5×5 のまま離散化して見せる(後者は安い)。`CourseGrid`・`aimCell`・CPU 投手(セル選択)・`cursorOf`・`useBattingControls` の相対ドラッグ(打撃で実装済み)の流用。守備レイアウトのゾーンが小さい(98×110px、低い画面で 62×69px)ので、**指でゾーンが隠れる**問題が出る。
- リスク: 大きい。ゾーン 98×110px は指(約 10〜20mm)より小さいので、相対ドラッグ+カーソルの拡大表示(または狙いのミニ表示)が必須。構図の再設計が要る(守備側のゾーンを大きく)。ゲート1でモック確認が必要([[visual-scope-must-be-shown-at-gate1]])。

### 案D: ワンジェスチャ投球(アプリの B タイプ相当)

- 内容: 球種チップを**押したまま**ゾーンへ指を動かし、離して投げる。ゲージは無し(または離す速度・位置で精度)。
- 効果: 中〜大(手数が 1 動作になり、テンポが良い)。腕前は「指の位置の精度」だけで、ゲージより弱い。
- 工数: M〜L(案 C の入力部分のみ)。リスク: 誤タップで投げてしまう(公式 FAQ も注意書きあり)。

### 参考の比較(推奨案の提示。決定は呼び出し元)

| 観点 | A | B | C | D |
| --- | --- | --- | --- | --- |
| 腕前の要素(#1) | なし | あり(ゲージ) | あり(位置+ゲージ) | 小(位置のみ) |
| 狙いの直接性(#3) | なし | なし | あり | あり |
| パワプロらしさ | 低 | 中 | 高 | 中 |
| 工数 | S〜M | M〜L | L | M〜L |
| 守備側の既存設計への影響 | 小 | 中(`PitchCommand`・判定) | 大(入力・構図・CPU 連携) | 中 |

- 推奨(参考): **A のうち A1・A3(+必要なら A2・A4)を先に入れ、B(または C)を主案としてゲート1でモック提示する**二段構え。A だけでは「腕前の要素」が戻らず、ユーザーの「パワプロとは程遠い」を解消しきれない可能性が高い(推測)。
- どの案でも、設計・テストで **人間を模した投球ボット**(ゲージ停止の時刻ばらつき、ドラッグの精度ばらつき、端末別の入力遅延)で、ストライク率・狙いセル到達率・打たれ方を数万球で試算する([[game-feel-needs-playability-check]])。
