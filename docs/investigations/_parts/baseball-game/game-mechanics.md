### Q1. パワプロの打撃操作の仕組み

| # | 事実 | 確度 | 出典 |
| --- | --- | --- | --- |
| 1.1 | 打撃は「ボールの移動に合わせてミートカーソル(打撃範囲)を動かして狙い、タイミングでスイングする」方式。カーソル中心付近の小さな点が最も飛ぶ「真芯」 | [WP] | Wikipedia「パワフルプロ野球シリーズ」 |
| 1.2 | **ミート打ち**はカーソルが大きく当てやすい(ヒット・単打向き)。**強振**はカーソルが小さく当てにくい代わりに長打(HR・二塁打)が出る。切替はコンソール版でR1/R2 | [公式] | WBSC eBASEBALL パワプロ プレイガイド(PDF) |
| 1.3 | カーソルは打者視点でストライクゾーン内に表示され、そこがバットの「芯」。大きさは選手の「ミート」能力と特殊能力で増減する(2020以降は低ミート帯で芯判定が狭まったという個人検証あり) | [攻略] 一次未確認 | ファミ通wiki、pawasuq、tell7171ブログ |
| 1.4 | **当たる位置と打球の質**: カーソル中心に当たると強い打球・ヒット性、上部ならフライ、下部ならゴロ、根元・先端は力のない打球。通常のミート(広いカーソル)は当てやすい分、打球が飛びにくい。※公式プレイガイドにも「中央の線より上=フライ、下=ゴロ」の記述があるとする検索要約と、ないとする要約が混在しており、公式記載の有無は未確認 | [攻略] | ファミ通wiki、pawasuq(バットに当てる位置) |
| 1.5 | **タイミング**: カーソル位置が合っていても、振りが早いと引っ張り方向のファウル/強い打球、遅いと逆方向のファウルになりやすい。多少の早打ちは「引っ張った強い打球」になる | [攻略] | ファミ通wiki |
| 1.6 | ミートカーソルは**横長**なので、真横に変化するスライダー・シュートは、縦に落ちる球種より打たれやすい(縦の変化に弱い) | [攻略] | gameranbu パワプロ2018 |
| 1.7 | 初心者向けに、カーソルが投球を追いかける「ロックオン」(アシスト強度が段階的)や、おおまかな位置を示す「フェードカーソル」がある。対戦(競技)設定ではどちらも無効 | [攻略] | Inside Games 2020 |
| 1.8 | 2020作以降、ストライクからボールになる球は、ミート能力に関係なく強振では当たらなくなった(個人の検証・見解) | [攻略] 要注意 | tell7171ブログ |
| 1.9 | **弾道**(1〜4等)は打球の軌道を決めるパラメータ。高弾道+高パワーでHR性の当たりが増え、高弾道でもパワーが低いとただのフライになる。HRは弾道×パワーの組み合わせで決まる | [攻略] | ニコニコ大百科「弾道」 |
| 1.10 | スマホ版は打撃をタップ/フリックで行い、**走塁・守備は基本オート**。試合は自動進行で、チャンス/ピンチの場面だけプレイヤーが操作する | [WP] | Wikipedia「実況パワフルプロ野球 (スマートフォン)」 |
| 1.11 | 能力値は基本1〜100(ランクG〜S)。ミート=当てる、パワー=飛ばす | [公式][攻略] | KONAMI公式、文春記事 |
| 1.12 | **打球の質(ゴロ/ライナー/フライ/HR)を決める内部式、芯の判定範囲の具体値、タイミング窓のミリ秒値は公開情報から確認できなかった** | 未確認 | 全検索で該当なし |

要点: パワプロの打撃は「(a)カーソルとボールの2次元距離で当たり/空振りと『芯からのズレ』が決まり、(b)カーソル内のどの高さに当たるかで打球の高低(ゴロ/ライナー/フライ)が、(c)スイングの早遅で方向(引っ張り/流し)とファウルが決まり、(d)能力値(ミート=カーソルの大きさ、パワー・弾道=飛距離と高さ)が打球の強さを左右する」という分解で説明できる(ただしこの分解は公開情報からの推測であり、内部式は未確認)。この分解自体は簡略化・再実装しやすく、案Cの骨格に使える。

### Q3. ブラウザで実装できる規模の簡略化1試合モード(提案)

#### 3-1. ルール案(全項目 [提案]。実在ルールの出典は§3-3)

| 項目 | 提案 | 備考 |
| --- | --- | --- |
| イニング数 | 開始時に**3回/5回/9回**から選択。既定は3回 | 所要時間の目安は§3-2 |
| 先攻後攻 | プレイヤーが選択。プレイヤーは**自軍の攻撃では打者、守備では投手**を担当し、CPUが逆側を担当 | 「CPU対戦の1試合モード」の要件 |

| 投球結果の種別 | ボール/見逃しストライク/空振り/ファウル/インプレー の5種 | スコアボードのB-S-O表示と整合 |

| 延長 | 最終回終了時に同点なら延長。既定は**最大3イニングまで延長し、延長初回から無死一・二塁のタイブレーク**。上限で同点なら引き分け | 高校野球は10回から無死一・二塁のタイブレーク。NPBは12回で引き分け |

#### 3-2. 所要時間の目安 [推定]

NPB 2024 の打席数は約63,762(両リーグ合計)で、1チーム1試合あたり約37打席、すなわち**1イニング(片側)あたり約4.1打席**。1打席の投球数を約3.8球(MLB一般値、[一般])、1球あたりの操作+演出を10秒(高速演出では5秒)と仮定すると:

| イニング数 | 総投球数(両軍) | 標準演出(10秒/球) | 高速演出(5秒/球) |
| --- | --- | --- | --- |
| 3回 | 約94球 | 約16分 | 約8分 |
| 5回 | 約156球 | 約26分 | 約13分 |
| 9回 | 約281球 | 約47分 | 約23分 |

→ ブラウザの1セッションとして、**既定3回(約10〜15分)**、9回は「じっくり派向け」と位置づけるのが妥当。「見逃し/ボール球の自動スキップ」「CPU攻撃時の演出短縮」で短縮余地がある。

#### 3-3. 実在ルールの参照(延長・コールド)

- 得点差コールド: 高校野球特別規則で「5回終了時に10点差以上、7回終了時に7点差以上」。選抜・選手権(甲子園)等では適用されない。 [攻略]
- 延長: NPBは原則12回まで、同点なら引き分け(2020〜21は特例で短縮)。高校野球のタイブレークは2018年導入(13回から無死一・二塁)、**2023年度から10回開始**に変更。 [攻略/報道]

安打種別と凡打種別ごとの**決定論的な進塁**を既定とする(Norvigの「Dice Baseball」やStrat-O-Maticの基本ルールと同系統: ヒットは打った塁数ぶん全走者が進む)。

| 単打 | 全走者+1塁。ただし**2塁走者は生還** | Norvigの採用解釈。「1塁走者を3塁へ」は確率オプション |
| 二塁打 | 全走者+2塁(2塁・3塁走者は生還、1塁走者は3塁) | |
| 三塁打 | 全走者生還 | |
| 本塁打 | 全走者+打者が生還 | |
| ゴロアウト | 1塁走者あり・2アウト未満なら**併殺**(p=0.45を既定値、[提案])。併殺でなければ走者は強制進塁分のみ+1(強い当たりは+1、弱い当たりは強制のみ) | MLB一般でGIDP機会の約半分程度が併殺になるという[一般]知識に基づく概算。要調整 |

| ライナーアウト | 走者は進塁しない | |
| 三振 | 走者は進塁しない | |
| エラー | 打者は1塁へ、全走者+1塁 | Norvig: エラーは全走者1塁進塁 |

#### 3-5. 守備を省略する場合の打球結果決定方法(3方式)

| 方式 | 概要 | メリット | デメリット |
| --- | --- | --- | --- |
| (i) 確率テーブル直引き | (打球タイプ, 強さ, 方向)を入力に、結果(アウト種別/安打種別/HR/エラー)を確率テーブルで抽選 | 最小実装、テーブルを調整するだけで難易度・得点環境を制御、テスト容易 | 打球の着地点と結果の因果が見えにくい |
| (ii) 落下地点グリッド+野手配置 | 打球を落下地点セルに落とし、野手が捕れるかを到達時間(野手の守備範囲)と滞空時間で判定 | 「野手の間を抜けた」等の説明が付く | 野手モデルが必要で中〜大規模。守備省略の意義が薄れる |
| (iii) ハイブリッド(推奨) | (i)で結果を決め、(ii)風の**演出**(打球方向と着地点)は結果から逆算して描く | 実装コストは(i)並み、見た目は納得感あり | 演出と結果の整合ルールが別途必要 |

### Q4. CPU側AI(既知の手法と難易度パラメータ)

#### 4-1. 既知の手法(ゲームAIの一般的手法) [一般] [攻略]

1. **重み付き乱数による配球**: 球種×コースの組に、カウント別の重み表を持たせて抽選する。電子野球ゲームの特許文献でも「CPU投手の球種は乱数で選ぶ」という最も単純な形が記述されている。実戦データではカウント別の直球比率が大きく異なる(後述 4-2)。
2. **人間らしい誤差の注入**: CPU打者を「完璧な判定」ではなく、**入力(カーソル位置・スイング時刻)にガウスノイズを加える**ことで人間らしくミスさせる。難易度は誤差のσで調整し、**最高難度でもσ=0にはしない**(下限を持つ)。
3. **複数パラメータの同時スケーリング**: 難易度を1つの係数で動かすのではなく、反応遅延・誤差幅・規律(見逃し率)等を、それぞれ常識的な範囲内で同時に動かす(単一パラメータを極端にするとバランスが崩れる)。
4. **CPUにも人間と同じ解決関数を通す**: CPU打者は「擬似入力(カーソル位置・スイング時刻)」を生成して**人間と同じ打席結果判定関数**に渡す。プレイヤーとCPUで判定規則が一致し、テストも1系統で済む。 [提案]
5. **プレイヤー側のアシスト**(ロックオン、MLB The Showの Zone/Directional/Timing の3モード、タイミング窓の拡大)は、人間側の難易度調整として確立している。
6. **動的難易度調整(DDA、ゴムバンド)**: 負けている側の確率補正等。公平感を損なうリスクがあるため既定では採用せず、オプション扱いが無難。 [提案]

## 選択肢の比較

### 比較1: 打席結果判定アルゴリズム(Q5。最重要)

- **案A(物理風)**: カーソルとボールの偏差、タイミング誤差から**打球の初速・角度・方向**を計算し、弾道を数値積分(空気抵抗等)して飛距離・滞空時間を求め、フェンスと野手の守備範囲で結果を決める。
  - 参考式[一般]: スイートスポットでの打球初速 ≈ 0.2×投球速度 + 1.2×バット速度(Nathan)。HR性の最適角度は約27〜28度(初速100mph、飛距離約400ft)で、効果の大部分は空気抵抗(Nathan, FanGraphs)。MLBの「Barrel」は初速98mph以上かつ角度26〜30度で必ず該当、初速が上がるほど許容角度が広がる(MLB Glossary)。
- **案B(確率テーブル)**: 距離・タイミング誤差から**質のスコア**を求め、段階(バケット)ごとの結果確率表(アウト種別/安打種別/HR等)を引いて乱数で決める。Strat-O-Matic(2ダイス+カード)が代表例で、投手と打者のカードを突き合わせて確率的に結果を決める。
- **案C(ハイブリッド、パワプロの分解を踏襲)**: 入力から**決定論的に**「接触の有無・打球タイプ(ゴロ/ライナー/フライ)・強さ段階・方向・ファウル有無」を決め、そのうえで**(タイプ, 強さ, 方向)をキーに確率テーブルを1回だけ抽選**して最終結果を決める。打球の軌道アニメーションは結果から逆算して描く。

| 評価軸 | 案A 物理風 | 案B 確率テーブル | 案C ハイブリッド |
| --- | --- | --- | --- |
| 実装コスト | **大**(軌道積分、フェンス、野手モデルが必須。守備省略なら「自動守備判定」も要る) | **小**(テーブルと乱数のみ) | **小〜中**(入力→段階変換の関数+テーブル) |

| 得点環境の制御(AVG/HR率) | 難(間接的) | **易**(表から逆算できる) | 易 |

#### 案Cの入力→結果の流れ(設計の骨格となる案) [提案]

1. **入力**: スイング種別(ミート/強振)、カーソル中心(cx, cy)、スイング時刻誤差 Δt(早い=負)、ボール最終位置(bx, by)、球速、球種、打者能力(ミート/パワー/弾道)。座標は上方向を正とするゾーン単位(ストライクゾーン=[−1,1]²)。
2. **接触判定**: 楕円距離 d = hypot((bx−cx)/rx, (by−cy)/ry)。カーソルは**横長(rx > ry)**。rx, ry はミート能力×スイング種別(ミート打ちは大、強振は×0.6〜0.7程度)で決める。d > 1 なら空振り。`|Δt|`が許容窓Tcontactを超えても空振り(窓の端はファウル寄り)。
3. **質**: q = (1 − d) × (1 − |Δt|/Tcontact)。d≒0 を「真芯」、窓の端は「当てただけ」。
4. **打球タイプ**: (by − cy)/ry が正側(球がカーソル中心より上)ならフライ寄り、負側ならゴロ寄り、中間はライナー(弾道パラメータで閾値をシフト)。
5. **方向**: Δtが負(早い)なら引っ張り、正(遅い)なら流し。窓の端で大きく外れたらファウル。
6. **強さ段階**: q × パワー × スイング種別補正 → 弱/中/強(+HR性)。
7. **最終抽選**: 表[タイプ][強さ][方向]から結果(凡打種別/単打/二塁打/三塁打/HR/エラー)を抽選。

## 推奨アプローチ

最終決定は設計フェーズ/人間が行う。調査者としての推奨は次のとおり。

1. **打席結果判定は案C(ハイブリッド)**を推奨。理由: ①パワプロの打撃の分解(カーソル位置→接触/質、高さ→打球タイプ、タイミング→方向/ファウル)をそのまま使え、②守備操作を省略する要件と相性が良く(案Aは野手モデルが必須)、③確率テーブル部分は表の調整とモンテカルロ検証で得点環境を制御でき、④入力→段階の写像が決定論で網羅テストしやすい。案Aは将来「守備操作の追加」をする場合の発展形として位置づける。
2. **ルールは§3-1の簡略化セット**(3/5/9回、先攻後攻選択、守備オート、盗塁/バント/継投はスコープ外、走者は決定論進塁、延長は上限付き+タイブレーク、コールドはオプション)を推奨。既定3回で約10〜15分のセッションに収まる。
3. **投球は案2-1(最終着弾点方式)+コントロールα(ガウス誤差)**でMVPを成立させ、案2-2(変化ベクトル)は次段の拡張とする。
4. **CPU AIは「重み付き配球表+入力ノイズ注入」で実装し、CPU打者も人間と同じ判定関数を通す**。難易度は§4-3の複数パラメータを同時に動かす。最高難度でもσに下限を設ける。
5. **ロジックは乱数源(RNG関数)を引数で受け取る純粋関数として仕様化**する(共有メモリ`pure-function-extraction`)。同じ入力+同じseedで結果が完全に再現でき、モンテカルロによるバランス検証が可能になる。
6. **著作権・商標面**: 名称・キャラ・UI・チーム/選手は全て独自(架空)にし、公開前に人間が最終確認する。

## 制約・リスク

- **一次資料未確認**: 本書の「パワプロの仕様」は検索要約由来で、特に打球判定の内部式、タイミング窓の具体値、投球コースの分割数は未確認。パワプロの再現ではなく「着想の借用」と位置づけ、数値は独自にチューニングする前提とすること。
- **入力遅延**: ブラウザ(特にタッチ/Bluetooth)では入力遅延が数十ms〜100ms程度生じ得る。パーフェクト窓を狭くしすぎると「押したのに空振り」の不満になる。MLB The Show 13 でも難易度全体でタイミング窓を広げて評価が上がった例がある。**窓幅は難易度パラメータとして外出しし、遅延補正(キャリブレーション)の余地を残す**([提案])。
- **バランス**: 確率テーブルの初期値は仮置き。得点環境(打率/HR率/三振率/四球率)が現実から大きく外れると面白さが損なわれるので、モンテカルロ(数万試合)での検証と、実プレイでの調整が必要。
- **所要時間**: 9回制は約23〜47分。ブラウザ向けには既定3回とし、演出の高速化/スキップ設定が必須。
- **CPUの公平感**: CPUが人間以上の情報(実際のボール位置を完全に知る)を使うのは問題ないが、誤差ゼロの「完璧な打者」は不満になる。ノイズの下限を設ける。DDA(ゴムバンド)は慎重に。
- **著作権/商標**: Q6の通り。実在名・パワプロ固有の名称/UI/キャラクターの使用は避ける。公開時は素材ライセンスの記録も必要。
- **スコープ膨張**: 盗塁、バント、継投、代打、守備操作は工数の分岐点。MVPでは「対象外」を設計書で明記すること。

## 未解決の疑問・要確認事項

1. 「パワプロ風」の許容範囲(UIの見た目をどこまで似せるか、名称に「パワプロ」を含めるか)の最終判断。**人間確認が必要**(本調査の推奨は、「パワプロ」の名称・キャラクター・UIを一切使わないこと)。
2. 既定のイニング数(3回)と、3/5/9のどれを選択可能にするかの確定。
3. 投球入力の方式(§比較2: 最終着弾点方式 か 変化ベクトル方式)と、ブレモデル(α/β)の確定。
4. プレイヤーの打撃入力の具体仕様(カーソル移動の方法=マウス/タッチ/キーボード、ロックオンのアシスト段階、スイング窓の既定値)。**入力デバイスの範囲は技術観点とUI設計に依存**。
5. 能力値の範囲と数(打者: ミート/パワー/弾道/走力、投手: 球速/コントロール/スタミナ/球種)と、架空チーム・選手データの作成方針(固定プリセット か ランダム生成か)。
6. 結果表(§案C)の初期値の妥当性。設計後、モンテカルロで検証してから実装に入る。
7. 一次資料の再確認(WebFetchが使えなかったため): ①KONAMI公式ヘルプ(打撃操作ページ)、②ファミ通wikiの打撃テクニックページ、③J-PlatPatでの「パワプロ」「実況パワフルプロ野球」商標の登録状況、④NPB/FanGraphsのタイプ別BABIP・進塁確率の最新値。
8. ゲーム状態として最低限持つべき項目(イニング/表裏/アウト/ボール/ストライク/走者3塁/回別得点/各軍打順/投球数/疲労)の型定義は、技術アーキテクチャ観点(shared 型)側と整合させる必要がある。
