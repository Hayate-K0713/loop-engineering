01 — Branch model

4つのブランチ、それぞれの持ち場

main と develop は「反映される場所」であり、誰も直接pushしない。実際の作業は feature/<topic-slug> か hotfix/<incident-slug> の上で行い、PR経由でしか main/develop に触れられない。

ブランチ役割直接push作成元
main 本番相当の安定ブランチ。常にデプロイ可能な状態を保つ。 禁止 —
develop 統合・検証用のブランチ。人間による動作確認("打鍵確認")の場。 禁止 main
feature/<topic-slug> 個々の変更(機能追加・改善・修正)用。既存の調査→設計→実装→テストサイクルをそのまま乗せる。 自ブランチのみ可 main
hotfix/<incident-slug> 障害復旧用。feature と同じ構造だが、調査・設計の厚みを簡略化してよい。 自ブランチのみ可 main

02 — Everyday work

feature のフロー

六角形(◇◇)は人間が判断する箇所。develop向け・main向けそれぞれに、CIグリーンの確認とAskUserQuestionによるマージ直前確認が独立して入る。

develop の打鍵確認は省略できない

develop へのマージが完了しても、それだけでは main 向けPRを作らない。sample-app にはまだ自動デプロイの仕組みがないため、確認方法(ローカルで develop を動かす・差分をレビューする 等)は都度人間の裁量に委ねているが、エージェントが代行・省略することは一貫して禁止している。

03 — Incident response

hotfix のフロー

/hotfix <incident> は /cycle と同じ4フェーズ・2ゲート・PR経由の反映を踏襲する。違うのは3点だけで、安全装置そのものを外すことは一度もない。

観点featurehotfix
ブランチ名 feature/<topic-slug> hotfix/<incident-slug>(ベースは常に main)
調査・設計の厚み 選択肢比較・リスク分析を尽くす 被害状況・原因・修正方針が伝われば最小限でよい
ゲート・レビュー・PR すべて実施 すべて実施(省略なし)
develop の打鍵確認 通常のペースで実施 迅速に、ただし省略はしない

速いのはドキュメント、安全装置ではない

簡略化してよいのは調査・設計ドキュメントの記述量であり、ゲートの回数やPRベースの反映そのものではない。障害対応の緊急性を理由に main/develop への直接pushやブランチ保護のバイパスを行うことは、意図的に禁止している。

04 — PR rules

PRルール

  1. main・develop への直接pushは禁止 すべての変更はPR経由で反映する。CLAUDE.md自体や .claude/・docs/ 配下のメタ編集も例外ではない(調査→設計→実装→テストの4フェーズは省略できるが、反映方法は同じPR経由)。
  2. CIグリーンが前提 .github/workflows/ci.yml の checks(typecheck/lint/test/build)・e2e(Playwright)がすべて成功していること。knip ジョブはレポート専用(continue-on-error)のため、必須チェックには含めていない。
  3. マージ実行の直前に、必ず人間へ確認 gh pr merge を叩く直前に AskUserQuestion で確認する。これは人間確認ゲート1・2とは別の、マージという不可逆性の高い操作に固有の確認ポイント。develop向け・main向けでそれぞれ独立に発生する。
  4. develop向けPRとmain向けPRは独立 技術的には develop 向けPRのマージは main 向けPR作成の前提条件ではない。ただし運用上は必ず「develop マージ → 人間の動作確認 → main 向けPR作成」の順序を守る。

05 — Defense in depth

三重の防御

「直接pushしない」は口約束ではない。同じルールを3つの独立した層で強制しており、1層をすり抜けても次の層で止まる。

①はエージェントの手順遵守、②はローカルのコマンド実行を機械的に止める仕組み、③はGitHub側でサーバーが強制する仕組み。管理者権限のトークンでも③はバイパスできない(enforce_admins: true)。

① 運用ルール

.claude/commands/release.md が、feature/hotfixブランチをpushしてからPR作成・CI確認・人間確認・マージまでの手順を定義する。エージェントはこの手順どおりに動く前提。

② PreToolUseフック

git push origin main・git push origin develop(明示指定・HEAD:main等のrefspec・--force/-f系・ブランチ未指定のまま保護ブランチにいる状態での bare git push)を検知して拒否する。feature/hotfixブランチへのpushは妨げない。

実録: このフック自身が最初のテストケースになった

このフックを書き終えた直後、それまでの習慣どおり git push origin main を実行したところ、書いたばかりのフックに即座にブロックされた。結果、その変更(フック追加を含む一連のコミット)自体を feature/git-workflow-pr-migration ブランチに退避し、PRとして反映する羽目になった — 図らずも、この文書が定義する手順そのものの最初の実地検証になった。

③ GitHub branch protection

main・develop それぞれに required_status_checks(typecheck / lint / test / build・Playwright e2e)・enforce_admins: true・required_pull_request_reviews.required_approving_review_count: 0(ソロメンテナのためレビュー必須数は0だが「PR必須」自体は有効)・force push禁止・削除禁止を設定済み。GitHubのref更新APIへ直接アクセスを試みると 422 Changes must be made through a pull request で拒否されることを確認している。

06 — Where things stand

現状ステータス(2026-08-13)

目標状態の定義から実装までの移行はすべて完了している。

  • ✓develop ブランチを main から作成・push
  • ✓/investigate・/cycle のブランチ命名を feature/<topic-slug> に変更
  • ✓/hotfix <incident> コマンドを新設
