調査から実装まで — 自律開発エージェントのパイプライン

1トピックについて /investigate から /test までを自律的に進めながら、 設計直後とテスト直後の2箇所だけで人間の承認を待つ。設計・実装の完了直後にはそれぞれ 別のサブエージェントによる自動レビュー(最大2ラウンド)も挟まる。調査開始の時点でトピックごとに隔離された git worktree(既定ブランチ main、指定があれば別ブランチ)に入り、設計・実装・テストまで同じワークツリーを使い続けるため、 他セッションと衝突しない。実装フェーズではメインエージェントは自分でコードを書かずタスク分割と並列dispatchに徹する。 実装対象は sample-app/(NestJS + Vite/React、TypeScript)— 静的解析・テストの方針を実地で検証するための最小構成。 frontend/backend間のAPI契約は shared パッケージの型を唯一の情報源にし、backend境界はDTO(class-validator)で検証する。

01

パイプライン全体 — トピック専用ワークツリー内

複数セッションが同じリポジトリを同時に修正する前提のため、調査開始の時点でトピック専用のgit worktreeに入り、設計・実装・テストまで同じワークツリーを使い続ける (以前は調査・設計だけベースブランチ直書きだったが、複数セッションが別topicを同時に調査すると docs/memory/MEMORY.md 等の共有ファイルが競合しうるため統一した)。 破線の丸ノードは人間を介さない自動レビュー、ひし形は人間確認ゲート。

git worktree で分離(調査開始時に作成)
git worktree add -b <topic-slug> .claude/worktrees/<topic-slug> <base-branch> → EnterWorktree(path: ...) · ベースブランチ側の共有ディレクトリのチェックアウト状態には触れない

STAGE 09

ワークツリー作成方式の変更(レースコンディション修正) 以前は共有ディレクトリで目的のブランチへcheckoutしてからEnterWorktree(name: ...)(worktree.baseRef: "head"、現在の実行ディレクトリのHEADから分岐)する方式だったが、複数セッションが同時に別々のベースブランチを指定するとcheckout同士が競合し、意図しないブランチから分岐しうるレースコンディションがあった。共有ディレクトリに一切触れず分岐元を明示指定できるgit worktree add -b方式に切り替えて解消した。
push は必須手順(ゲート2承認・メタ編集完了に含まれる) マージ完了後の origin への push は、以前は人間の別指示を待つ任意の後片付けだったが、ローカルにcommitだけが積まれoriginが古いまま取り残される事故(GitHub Pagesが数コミット分古い内容を配信し続けた)を受けて必須手順に変更した(CLAUDE.md厳守ルール8)。ゲート2「承認してクローズ」後のマージ、およびCLAUDE.md/.claude/docs配下のメタ編集(ルール7の例外ルート)でのcommit後は、いずれも人間から改めて「pushして」と言われるのを待たず git push origin <base-branch> まで実行してから完了報告する。pushされたタイミングで .github/workflows/ci.yml が typecheck・lint・test・build・E2Eを実行し、ここまでの自動チェックを適用する。
修正依頼 / 設計からやり直し ワークツリーは削除せずそのまま残し、同じブランチ内で /implement または /design をやり直してから再びゲート2に戻る。新しいワークツリーは作り直さない。
ゲート2の判断ベースブランチへのマージワークツリー次のアクション
承認してクローズする削除サイクル完了を報告
修正依頼しない維持/implement に戻り同じブランチで修正
設計からやり直ししない維持同じブランチ内で設計書を修正 → /implement

設計レビュー・コードレビューの各ラウンドの判定は設計ドキュメントの「設計レビュー結果」「コードレビュー結果」欄に、未解決のまま引き継がれた指摘はテストレポートの「コードレビューからの引き継ぎ」欄に記録される。 同一ゲートの「人間確認ゲート記録」が3行以上(承認以外の判断が2回以上)になったら、/cycle はサイクルを中断して根本原因を人間と整理することを提案する。

03

調査の並列化(ファンアウト)

  1. 分解条件 — 互いに依存せず独立して調べられる観点が2〜4個ある場合のみ分解する
  2. 出力先を明示 — 観点ごとに docs/investigations/_parts/<topic-slug>/<sub-slug>.md を指定し、investigator自身には決めさせない
  3. 並列実行中は共有メモリに直接書き込まない — 知見は「メモリ候補」として最終報告に含める
  4. 統合 — 全観点が揃ったら1つの調査ドキュメントにまとめ、矛盾は「未解決の疑問」として残す
.claude/commands/investigate.md:14,28–32,36,43
04

再利用パターンのSkill化

convention/pitfallエントリが3つ以上の異なるtopicで再利用されたら、単なる知識共有を超えて手順(Skill)へ格上げする候補として扱う。 自動では作成しない — 検知から作成まで、必ず人間承認を挟む。

  1. 検知 — convention/pitfallエントリを適用するたび、related_topics に今回のtopic-slugを追記する
  2. 閾値 — related_topics が3つ以上の異なるtopicに達したら「スキル化候補」
  3. 提案のみ — その場ではSkill化せず、成果物ドキュメントの末尾と報告に候補として明記する
  4. 人間承認 — 次の人間確認ゲート(通常ゲート1)で AskUserQuestion により「Skill化する/しない/保留」を確認する
  5. 作成 — 承認された候補のみ、メインエージェントが .claude/skills/<name>/SKILL.md を作成する
  6. 記録 — 元のメモリエントリは削除せず status: promoted-to-skill にし、MEMORY.md にも反映する

MUST

ゲート1・ゲート2を通過する前に、次のフェーズへ自動的に進んではならない。承認は必ず AskUserQuestionで明示的な選択肢として取得し、曖昧な確認で済ませない。 CLAUDE.md:27–31(厳守ルール)

MUST

スラッシュコマンドを使わず自然言語で実装・修正を依頼された場合も、対象が実装対象プロジェクトのコード変更であれば /cycle と同じ全工程(調査→設計→ゲート1→実装→テスト→ゲート2)を起動しなければならない。「軽微だから」を理由に 直接ファイルを編集して済ませてはならない(CLAUDE.md自体・.claude/・docs/配下の運用ルールのメタ変更は対象外)。 このルールは口頭の指示だけでなく、.claude/settings.json の PreToolUse フック(Write|Edit・Bash)による機械的な二重防御でも担保されている — sample-app/・.github/workflows/配下のファイルをトピック専用ワークツリー外で編集・コミットしようとすると、hookがdenyで強制ブロックする。 CLAUDE.md:厳守ルール7 · .claude/settings.json

MUST

ローカルにcommitしただけで作業を終えてはならない。 ゲート2「承認してクローズ」でのマージ後、および CLAUDE.md自体・.claude/・docs/配下のメタ編集(厳守ルール7の例外ルート)でのcommit後は、 いずれも人間から改めて「pushして」と言われるのを待たず git push origin <base-branch> まで実行する。 ローカルcommitのみが積み重なりoriginが古いまま取り残されると、GitHub Pages等originに依存する仕組みが古いまま放置される (実際に8コミット分のpush漏れでGitHub Pagesが古い内容を配信し続けた事故が発生している)。 CLAUDE.md:厳守ルール8 · docs/memory/entries/unpushed-local-commits-stale-origin.md

既知の制限
  • あるトピックのワークツリーは、作成された時点のベースブランチの状態(特に docs/memory/)を引き継ぐ。作成後にベースブランチへマージされた他トピックの決定・規約は自動反映されない(通常の git worktree の性質上の制限)。長時間かかるトピックでは、途中でベースブランチの最新を取り込むべきか判断してよい。
  • 複数トピックのブランチが同時にベースブランチへマージされる場合、docs/memory/MEMORY.md など共有ファイルでマージコンフリクトが起きうる。この場合も自動解決せず人間に報告する。
