# grilling: 計画をラウンド単位で詰める壁打ちスキル

出来上がった計画・設計・結論を性急に承認せず、**壊れる条件を探すことで確度を上げる**ための壁打ち手法。褒めない。前提を表に出し、反証を試みる。

## 基本作法

- 対象の計画を**設計ツリー**とみなす。各決定は、その決定に依存する下位の決定へ枝分かれする。
- **フロンティア**(前提となる決定がすでに確定していて、今すぐ聞ける質問群)を1**ラウンド**でまとめて提示する。他の未回答の質問に依存する質問は、そのラウンドには含めず後続ラウンドに回す。
- 各問いに**番号(Q1, Q2, …)と推奨の答え(仮説)を添える**。ユーザーが「それでいい/違う、こう」で即座に進められるようにする。フォーマット例:

  ```
  ❓ **Q1** - <質問タイトル>: <質問本文。複数選択肢がある場合は列挙する>

  ➡️ <推奨する答え>

  ---

  ❓ **Q2** - <質問タイトル>: <質問本文>

  ➡️ <推奨する答え>
  ```

- 答えで分かることは聞かず**自分で調べる**(コードベース・既存ドキュメント・`docs/memory/`を先に見る)。調査中の項目はフロンティアの外に置き、それに依存しない他の質問は先に出す(調査待ちを理由に全体を止めない)。
- **隠れた前提を表に出して反証する。** 「その前提が崩れる条件は?」を必ず問う。
- 裏取りが必要な主張は断定のまま進めない。
  - コードベース内の事実 → Grep/Read で確認
  - 一般的な事実・仕様・ライブラリの挙動 → WebSearch/WebFetch
  - それでも確認できない場合は `[要検証]` タグを付けて先へ進む(人工的に確定させない)
- 1ラウンドの回答を受け取ったら、それによって解決した決定を確定させ、新たに前提が揃った質問(次のフロンティア)を再計算して次のラウンドを出す。
- **終了条件**: フロンティアが空になっている(決定木の各項目が「裏取り済み」か `[要検証]` のいずれかの状態)こと。全項目を尽くす必要はなく、ユーザーが「もう十分」と言えばそこで区切ってよい。

## 決定木(ソフトウェア計画向け)

計画・設計ドキュメントを枝ごとに潰す。各枝は「①現状の記述→②隠れた前提の抽出→③反証→④裏取り(必要時)→⑤確度タグ付け」の順で進める。以下の6分岐は相互にほぼ独立しているため、初回ラウンドでは根拠が薄い枝の質問をまとめて出してよい。あるステップの回答が別の枝の質問の前提になる場合(例: スコープの確定が実装ステップの粒度に影響する)は、その質問を後続ラウンドに回す。

1. **スコープ(やること/やらないこと)**
   - 「やらないこと」に分類したものは本当に後回しにできるか?今回の変更と密結合していないか?
   - 反証: 「後でやる」が実質「やらない」になっていないか。
2. **前提・制約**
   - この計画が成立する前提は何か?その前提が崩れたらどうなるか?
   - 明文化されていない制約(パフォーマンス、既存機能への影響、後方互換性、セキュリティ)はないか?
3. **実装ステップの妥当性**
   - 各ステップは独立して検証可能か?このコンテキストを持たない実装者が読んで迷わない粒度か?
   - 依存関係(順序・並列化できるか)は明示されているか?
4. **テスト戦略**
   - 「合格」の基準は、誰が判定しても同じ結果になるほど具体的か?
   - 自動テストを書かない場合、その理由は本当に妥当か(安易な「しない」への反証)?
5. **リスク・ロールバック**
   - 最悪のケースで何が壊れるか?ロールバックは実際に実行可能な手順になっているか?
6. **代替案**
   - 比較した選択肢は妥当な代替か?比較なしの一択(決め打ち)になっていないか?

観点はこの6つに固定する必要はない。対象の計画の性質に応じて枝を追加・省略してよいが、省略した場合はその旨を一言添える。

## 出力

壁打ちの結果は、呼び出し元のドキュメント(設計ドキュメント等)の該当箇所に直接反映する。壁打ちのやり取り自体を新しいファイルとして残す必要はない。`[要検証]` が残った項目は、ドキュメントの「リスク・トレードオフ」または「未解決の疑問」に明記する。

## 注意

- 答えをこのスキル自身が代わりに出さない。妥当性の検証に徹し、代替案の最終選択は呼び出し元(人間)に委ねる。
- 詰問調にしない。「なぜ考えていないのか」ではなく「ここが崩れる条件を一緒に確認しよう」というトーンを保つ。
- 事実確認は自分の仕事であり、ユーザーに調べさせない。調べれば分かることを質問に混ぜない。
- このスキルは`docs/process/agent-cycle.md`が定義する人間確認ゲート(設計後・テスト後の2箇所)を代替・追加するものではない。ゲートに至る前のドラフトの質を上げるための技法であり、壁打ちの完了自体が承認を意味しない。
