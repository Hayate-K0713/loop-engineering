あなたはこれから「調査・設計・製造・テスト」の1サイクルを、対象トピックについて最初から最後まで実行する。

トピック: $ARGUMENTS

## 実行順序

1. `/investigate $ARGUMENTS` の内容に沿って調査を行い、`docs/investigations/` に記録する。**この最初のステップでトピック専用の git worktree を作成し、以降このサイクル全体(設計・実装・テスト)を通じて同じワークツリー内で作業する**(詳細は `.claude/commands/investigate.md` の「ワークツリーの分離」)。ベースブランチは既定で `main`、ユーザーが別ブランチを指定していればそちらを使う。
2. `/design $ARGUMENTS` の内容に沿って設計を行い、`docs/designs/` に記録する。**手順1で作成したワークツリー内でそのまま継続する**(再度ワークツリーを作る必要はない)。**設計完了後、人間確認ゲートの前に `design-reviewer` サブエージェントによる自動レビュー(最大2ラウンド)を挟む**(詳細は `.claude/commands/design.md`)。
3. **人間確認ゲート1**: `AskUserQuestion` で設計の承認を得る(承認/修正依頼/差し戻し)。設計レビューで未解決のMAJOR指摘があれば、その内容もここで提示する。**スキル化候補(同じconvention/pitfallが3topic以上で再利用された)があれば、その内容もここで提示し、Skill化の可否を別途確認する**(詳細は `.claude/commands/design.md`、`docs/process/shared-memory.md`の「再利用パターンのSkill化」)。承認が得られるまで手順4に進んではならない。修正依頼・差し戻しの場合は該当フェーズに戻ってやり直し、再度このゲートに戻る。
4. `/implement $ARGUMENTS` の内容に沿って実装する。**既に手順1で作成したトピック専用のワークツリーに入っているはずなので、そのまま継続する**(入っていなければ既存ワークツリーを確認して入り直す、詳細は `.claude/commands/implement.md`)。複数セッションが同時に別トピックを実装しても、それぞれ別のワークツリーで作業するため衝突しない。**このステップを実行するメインエージェント自身はコードを書かない。** `TaskCreate` で設計をタスクに分割し、依存のないタスクは `implementer` へ並列dispatchし、`TaskList`/`TaskUpdate` で進捗を確認する役割に徹する。**実装完了後、`/test` に進む前に `code-reviewer` サブエージェントによる自動レビュー(最大2ラウンド)を挟む。**
5. `/test $ARGUMENTS` の内容に沿って、手順1で作成したトピック専用ワークツリー内でテストし、`docs/tests/` に記録する。コードレビューで未解決のMAJOR指摘があれば、テストレポートに引き継いで明記する。
6. **人間確認ゲート2**: `AskUserQuestion` でテスト結果の承認を得る(承認してクローズ/修正依頼/設計からやり直し)。承認が得られるまでこのサイクルを完了扱いにしてはならない。修正依頼・差し戻しの場合は該当フェーズ(手順4または2)に戻り、ワークツリーはそのまま維持して作業を続け、再度ゲート2に戻る。
7. 承認が得られたら、`.claude/commands/release.md` の手順に従い、トピックのブランチをPR経由で `develop` → `main` の順に反映する(直接pushは行わない。詳細は `docs/process/git-workflow.md`)。`develop` 向けPR・`main` 向けPRそれぞれについて、マージ実行直前に必ず `AskUserQuestion` で人間に確認する。`develop` へのマージ後は、人間による動作確認("打鍵確認")が完了するまで `main` 向けPRを作成しない。マージがコンフリクトした場合、またはCIチェックが失敗した場合は自動解決・無視をせず人間に報告する。
8. `main` へのマージ・ワークツリー削除が完了したら、サイクル完了を宣言し、成果物(調査・設計・テストの各ドキュメントへのパス、`develop`・`main` それぞれのPRへのリンク)を要約して報告する。

## 運用上の注意

- 各フェーズは可能な限り対応するサブエージェント(`.claude/agents/investigator.md` 等)に委譲し、メインの会話コンテキストを圧迫しないようにする。ただし委譲する場合も、ゲートでの人間確認は必ずメインの会話(このコマンドを実行しているセッション)で行うこと。委譲先のサブエージェントに承認判断をさせてはならない。
- `EnterWorktree`/`ExitWorktree` はこのメインセッション自身の作業ディレクトリを切り替えるツールである。`/investigate`の時点でワークツリーに入り、`/design`・`/implement`・`/test`はそれを引き継ぐ。`investigator`・`designer`・`implementer`・`tester`サブエージェントに委譲する場合、委譲はメインセッションがワークツリーに入った**後**に行い、サブエージェントがそのワークツリー配下で作業するようにすること。
- 各フェーズ(サブエージェントに委譲する場合はその内部)は `docs/memory/MEMORY.md` を介して知識を共有する。あるフェーズで得られた再利用可能な知見(decision/convention/pitfall/glossary/open-question)は、そのフェーズの完了時点で `docs/memory/entries/` に反映されている前提で次フェーズに進んでよい。サイクル全体が終わったら、`docs/memory/MEMORY.md` に新規・更新エントリがあれば要約に含めて人間に報告する。
- 手順の途中で致命的な不確実性(要件不明、認証情報が必要、破壊的操作が必要 等)にぶつかった場合は、定義されたゲート以外の場所でも停止して人間に確認してよい。
- 何度もゲートで差し戻しが続く場合は、一旦サイクルを中断し、根本原因(要件定義そのものが曖昧である等)を人間と一緒に整理することを提案する。**「何度も」は感覚ではなく、設計ドキュメント/テストレポートの「人間確認ゲート記録」テーブルの行数で判定する。同一ゲートの記録が3行以上(承認以外の判断が2回以上)になったら中断を提案する。**
- `design-reviewer`・`code-reviewer` によるレビューは**人間確認ゲートではなく、自動で完結するチェック**である。人間確認ゲートは引き続き2箇所(設計後・テスト後)のみ。レビューで解消しきれなかった `MAJOR` 指摘は、必ず直後の人間確認ゲートの提示内容に含め、隠したまま承認だけ求めない。
- 手順4(`/implement`)を実行するメインエージェントは、**自分でファイルを編集・作成して実装してはならない。** 必ず `TaskCreate` でタスクに分割し `implementer` に委譲する。タスクが1つしかない場合も例外なく委譲する。メインエージェントの役割はタスク分割・並列dispatch・`TaskList`/`TaskGet`による進捗確認・完了報告受領後のコミットに限られる。
