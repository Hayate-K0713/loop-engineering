あなたはこれから「調査」フェーズを実行する。対象トピックは以下の通り。

トピック: $ARGUMENTS

## ワークツリーの分離(必須・調査開始前に必ず行う)

このプロジェクトは複数セッションが同時に同じリポジトリを修正することを想定している。**`/investigate`・`/design`もベースブランチの共有ディレクトリで直接ファイルを書かず、`/implement`・`/test`と同じトピック専用の git worktree の中で行う。** ワークツリーは調査開始時に一度だけ作成し、`/design`→`/implement`→`/test`まで同じものを使い続ける。

`.claude/skills/topic-worktree/SKILL.md` の `topic-worktree` スキルを、以下のパラメータで呼び出す。

- `topic-slug`: 対象トピックのslug
- `branch-prefix`: `feature`(障害対応として `/hotfix` から呼ばれている場合は `hotfix`。詳細は `.claude/commands/hotfix.md`)
- `base-branch`: 既定は `main`。ユーザーが `$ARGUMENTS` や直近の会話で明示的に別のブランチを指定していれば、そちらを使う

このスキルが、既存ワークツリーへの入室・別トピックからの`ExitWorktree`・新規作成(`git worktree add -b`)・`EnterWorktree`までを行う。以降の設計・実装・テストはすべてこのワークツリー内で行う(`/design`・`/implement`・`/test` も同じ `topic-slug` で同スキルを呼び出すだけでよく、再作成は起きない)。

## 手順

1. `docs/memory/MEMORY.md` を読み、既存の decision / pitfall / glossary で関連するものがあれば `docs/memory/entries/` の詳細も確認する。**convention/pitfallエントリを実際に調査の判断材料として適用した場合、そのエントリの frontmatter `related_topics` に今回のtopic-slugを追記する**(まだ含まれていなければ)。追記の結果 `related_topics` が3つ以上の異なるtopicを含むに至ったら「スキル化候補」として控えておく(手順6で報告する。詳細は`docs/process/shared-memory.md`の「再利用パターンのSkill化」)。
2. `docs/templates/investigation-template.md` を読み、テンプレート構成を把握する。
3. **トピックが分解できるか判断する。** トピックの中に、互いの結果を待たずに独立して調べられる観点が2つ以上あるか確認する(例:「ライブラリ選定」と「既存アーキテクチャとの整合性」と「パフォーマンス制約」)。観点同士が強く依存する場合(片方の結論がもう片方の調べ方を左右する)や、観点が実質1つしかない場合は分解しない。分解する場合も観点は2〜4個程度に留める。多すぎると統合コストが調査コストを上回る。

### 3a. 分解しない場合(通常調査)

自分自身で、または investigator サブエージェント1体への委譲で、以下を組み合わせて調査する。

- 既存コードベースの探索(該当機能が既にあるか、関連する実装・設定はどこにあるか)
- Web調査(ライブラリの選定、公式ドキュメント、既知の落とし穴、代替アプローチの比較)
- 制約条件の洗い出し(依存関係、パフォーマンス、セキュリティ、既存アーキテクチャとの整合性)

手順4に進む。委譲する場合、共有メモリへの読み書き(手順1・6)は investigator が自分で行ってよい(通常の単独呼び出しのため)。

### 3b. 分解する場合(並列調査 / ファンアウト)

観点ごとに `investigator` サブエージェントを **同一メッセージ内で複数回呼び出し、並列に実行する**(Agent toolを1つのレスポンス内で複数回呼ぶ)。各呼び出しのプロンプトには必ず以下を明示する。

- 調べるべき観点(スコープを絞った具体的な問い。他の観点の調査結果には依存しないこと)
- 出力先パス: `docs/investigations/_parts/<topic-slug>/<sub-slug>.md`(最終統合ドキュメントではなく観点ごとの作業ファイル。パスは呼び出し元が指定し、investigator自身には決めさせない)
- 「これは並列調査の一部であり、`docs/memory/` への直接書き込みは行わないこと。再利用可能な知見があれば、書き込まずに最終報告のテキストに『メモリ候補』として明記すること」という明示的な指示。理由: 複数のサブエージェントが同時に `docs/memory/MEMORY.md` を編集すると内容が競合・上書きされるため、書き込みは必ずorchestrator(このメインの会話)が後でまとめて行う。

全呼び出しの完了を待ってから手順4に進む。

4. 【3bの場合のみ】各観点の作業ファイル(`_parts/`)とサブエージェントの最終報告を読み合わせ、矛盾がないか確認する。観点間で結論が食い違う場合、どちらかを黙って採用せず「未解決の疑問」として明記する。
5. 調査結果(3aまたは4)を `docs/investigations/YYYY-MM-DD-<topic-slug>.md`(実行日・topicから機械的に決める)にテンプレートへ沿って統合・記録する。特に以下は必ず埋める。
   - 背景・目的(なぜこの調査が必要か)
   - 選択肢の比較(最低2案。比較なしの一択決め打ちは避ける)
   - 推奨アプローチとその理由
   - 未解決の疑問・要確認事項(あれば)
   - 3bの場合: 各観点の作業ファイル(`_parts/...`)へのリンク
6. topicを超えて再利用できる知識(decision/pitfall/glossary)を得た場合は、`docs/memory/templates/entry-template.md` を使って `docs/memory/entries/` に追記し、`docs/memory/MEMORY.md` の索引を更新する。**3bの場合、これは各investigatorではなくorchestrator(このメインの会話)が行う。** 各investigatorから返された「メモリ候補」を集約し、重複・矛盾を解消してから1回で書き込む。手順1でスキル化候補が見つかった場合は、Skillファイルをここで作成せず、調査ドキュメントの末尾と会話への報告に「スキル化候補: [[entry-name]](related_topics N件)」として明記するに留める(実際の作成は次の `/design` の人間確認ゲートで承認を得てから)。

## 完了条件

- トピック専用のワークツリー(`.claude/worktrees/<topic-slug>`)内で作業していること(上記「ワークツリーの分離」参照)
- `docs/investigations/` に調査ドキュメントが保存されていること
- ドキュメントの末尾に「次のアクション: `/design` で設計フェーズに進む」という一文を含めること
- スキル化候補(手順1・6)があれば、ドキュメント末尾と会話への報告にその旨が明記されていること

## 注意

- このコマンド自体はゲート(人間確認)を挟まない。調査完了後は自動的に次(`/design`)へ進んでよい。ただし調査の過程で要件が根本的に不明な場合は、調査を終える前に人間に質問してよい。
- ファンアウト(3b)は「独立した観点が複数ある」場合の高速化手段であり、常に使うものではない。単一の観点しかないトピックで無理に分解しない。
- `/design` はこのワークツリーをそのまま引き継ぐ(詳細は `.claude/commands/design.md` の「ワークツリーの確認」)。再度 `EnterWorktree` で新規作成する必要はない。
